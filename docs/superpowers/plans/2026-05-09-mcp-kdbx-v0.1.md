# mcp-kdbx v0.1 Implementation Plan

> **Status (2026-06): Phases 1-3 complete** on branch `feat/v0.1` (tasks 1-18; the task 11 idle timer landed as part of the Phase 3 adapter). All 17 tools serve over real stdio MCP via `rmcp` 1.7.0, 179 lib tests pass, fmt and clippy are clean, and end-to-end validation confirmed zero plaintext leakage. Phases 4 (tasks 19-22: fixtures, integration tests, protocol conformance, manual smoke) and 5 (tasks 23-26: CI gates and docs) remain. Checkboxes below were not ticked during execution; CLAUDE.md "Status" is the live source of truth, including the three deliberate deviations from this plan's letter (module named `kdbx_core` not `core`; diff-kdbx dep added in Phase 2; tool surface split across `src/adapter/{lifecycle,reads,reveals,writes}.rs` instead of one `tools.rs`).

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build mcp-kdbx v0.1: a stdio MCP server exposing 17 tools across four categories (lifecycle, read, reveal, write) over a KeePass `.kdbx` vault, with per-secret consent gating and a JSONL audit trail.

**Architecture:** Single Rust binary, stdio JSON-RPC. Direct dependency on `keepass-rs 0.12.5+` (with `serialization` and `save_kdbx4` features) for vault operations and on `diff-kdbx` (as library) for stage diffs. Internal `kdbx_core` module isolated from MCP types so a future `serv-kdbx` HTTP adapter can reuse the core. Full v0.1 design lives at `docs/superpowers/specs/2026-05-08-mcp-kdbx-design.md`.

**Tech stack:** Rust 1.85+, edition 2024. Library deps: `keepass`, `diff-kdbx` (path or git), `tokio` (async runtime), `serde`, `serde_json`, an MCP framework (`rmcp` or hand-rolled JSON-RPC over stdio; choose during Phase 1), `chrono`, `uuid`, `sha2`, `tracing`, `tracing-subscriber` for the audit log. CLI deps: `anyhow`. Test deps: `tempfile`, `assert_cmd`, `predicates`, `proptest` (for v0.2; not used in v0.1).

**Spec:** `docs/superpowers/specs/2026-05-08-mcp-kdbx-design.md`

**Exclusions (from spec):** No HTTP/SSE transport. No multi-vault. No delete/move/rename tools. No force-overwrite on save conflict. No snapshot-based diff. No `mlock`. No tamper-evident audit log. No rate limiting. No `KDBX_PARANOID` shorthand. No property tests in v0.1. No `.env` parsing built in. No Windows.

**API surface caveat:** keepass 0.12.5 write API is stable as of the recently-merged PR #321 (`EntryRef::attachments_named()`). The write API used: `Database::iter_all_entries/groups`, `Database::entry_mut/group_mut`, `EntryMut::edit(closure)`, `EntryMut::set(name, Value::protected/unprotected(value))`, `Database::save(&mut Write, DatabaseKey)`. `DatabaseKey` is `Clone + Default + Zeroize`; clone-per-save is the documented path.

**diff-kdbx as library:** the library API for semantic-diff between two `keepass::Database` instances must be exposed. If the existing diff-kdbx crate exports it, use directly. If not, file an issue/PR upstream (in our own repo) before this plan starts; the dependency is co-designed across both projects.

**MCP framework choice (Phase 1 decision):** evaluate `rmcp` (the official-ish Rust MCP SDK) versus a hand-rolled JSON-RPC-over-stdio loop. `rmcp` saves boilerplate but couples us to its API surface. Hand-rolling is ~200 LOC of code we control. Pick during Task 1; document the choice and rationale in the resulting commit.

**Audit invariants (must hold at every commit):**
- `kdbx_core` does not import any MCP-specific types. Tested by separation: `kdbx_core` compiles standalone if extracted as a separate crate.
- Reveal events log a sha256 of the value, never the value. CI grep checks this in code: any string containing the word "log" near a reveal handler MUST also contain "sha256" or be in a test file.
- `kdbx_unlock` parameter `password` is redacted in any `mcp_message` capture path.
- `KDBX_ALLOW_WRITES` is checked at every write-tool entry point.

## Implementation order recommendation

Sequential by phase (each phase depends on earlier ones):

**Phase 1 (Tasks 1-9):** Scaffolding and core types. ~50% of v0.1 LOC. No MCP layer; native Rust only.
**Phase 2 (Tasks 10-13):** Stage-then-commit semantics. Builds on Phase 1's vault state machine.
**Phase 3 (Tasks 14-18):** MCP adapter layer. Builds on Phases 1-2.
**Phase 4 (Tasks 19-22):** Tests. Layer 2 + Layer 3 coverage; Layer 4 manual smoke documented.
**Phase 5 (Tasks 23-26):** CI gates and documentation polish.

Phases 1, 2, and 3 can be subagent-driven, one task per dispatch with two-stage review. Phase 4 may benefit from parallel dispatches (file-disjoint integration test files). Phase 5 is sequential polish.

Total estimated tasks: 26. Estimated LOC delta: +3500 to +4500 across Rust + tests + docs + scripts. Higher than the spec's "~2000 LOC" estimate because that figure was for the core happy path; the integration test suite and protocol-conformance harness add another 1000-1500 LOC.
